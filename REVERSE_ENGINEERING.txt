--------------------------------------------------------------------------------
1. THE ONE IDEA (start here when lost)
--------------------------------------------------------------------------------
Question the whole app answers:

  "Can I keep a meaningful, offline field log of outdoor life — hikes, climbs,
   snowboard days, camps, range sessions, hunts, water — and see my own
   consistency and personal peaks without turning it into a vanity social feed?"

If a feature does not improve honest logging, activity-specific truthfulness,
local ownership of data, map memory, or motivation-with-integrity (streaks/
milestones that serve purpose, not dopamine farms), it does not belong.

That filter stops INFJ overbuilding (no cloud sync theater, no leaderboards,
no generic purple Material clone, no "AI coach").

3. STATE MANAGEMENT — WHY RIVERPOD
--------------------------------------------------------------------------------
File: lib/providers/providers.dart

  databaseProvider          → owns AppDatabase lifecycle (close on dispose)
  sessionRepositoryProvider → wraps CRUD
  sessionsProvider          → StreamProvider from repository.watchAll()
  dashboardStatsProvider    → whenData(DashboardStats.fromSessions)
  seedProvider              → FutureProvider one-shot seedIfEmpty()
  shellTabProvider          → which bottom tab is active

Why Riverpod (recommended here):
  1. Explicit dependency graph — DB → repo → stream → derived stats
  2. No BuildContext required to read/write outside widgets
  3. StreamProvider matches Drift's reactive queries naturally
  4. Easy to unit-test DashboardStats without Flutter widgets
  5. ProviderScope at root keeps the app demo-simple (no codegen required
     for these providers — riverpod_generator is available if you grow)

Not chosen: setState-only (won't scale across map + chart + form),
Bloc (more ceremony for a single-user offline log), GetX (weaker for
portfolio signal of deliberate architecture).


--------------------------------------------------------------------------------
4. DATA MODEL — SHARED + ACTIVITY-SPECIFIC
--------------------------------------------------------------------------------
Domain types:
  lib/domain/activity_type.dart   — enum + icons + field specs
  lib/domain/session.dart         — AdventureSession
  lib/domain/dashboard_stats.dart — streaks, PRs, milestones (pure functions)

Drift table: lib/data/database/tables.dart → Sessions

SHARED COLUMNS (always meaningful / queryable)
  id                text PK (uuid)
  activityType      text  (hike|climb|snowboard|camp|shoot|hunt|jetski|other)
  title             text
  startedAt         datetime
  durationMinutes   int
  locationName      text?
  latitude          real?
  longitude         real?
  notes             text?
  difficulty        int 1–5
  elevationGainM    real?   ← shared metric for trail/wall/snow
  distanceKm        real?   ← shared metric for trail/water
  detailsJson       text    ← activity-specific map as JSON
  createdAt / updatedAt

ACTIVITY-SPECIFIC (examples in detailsJson)
  hike       → trailName, elevationGainM, distanceKm
  climb      → routeGrade, pitches, elevationGainM
  snowboard  → snowConditions, verticalDropM, resort
  camp       → nightsOut, siteName
  shoot      → rangeDistanceM, firearmType, roundsFired
  hunt       → terrain, gameType
  jetski     → waterConditions, distanceKm

Design rule:
  Promote metrics you chart/PR into real columns (elevation, distance).
  Keep the weird, type-native fields in JSON so the schema stays honest
  without a dozen nullable columns nobody queries.


--------------------------------------------------------------------------------
5. STORAGE — DRIFT (SQLITE), NOT HIVE
--------------------------------------------------------------------------------
Files:
  lib/data/database/app_database.dart   (+ generated app_database.g.dart)
  lib/data/session_repository.dart

Choice: Drift over Hive for this use case.

  Drift wins when you need:
    · Ordered history (ORDER BY startedAt DESC)
    · Aggregations later (SUM elevation, COUNT by type) in SQL if you grow
    · Migrations when the log schema evolves
    · Type-safe Dart API over SQLite (portfolio-credible persistence)

  Hive wins when you need:
    · Simple key-value / prefs / cache blobs
    · Minimal relational thinking

  Wild Log is an expedition log + dashboard. That is relational + analytic.
  Use Drift. (You can still add Hive later for UI prefs only.)

Seed: AppDatabase.seedIfEmpty() inserts PNW-flavored demo sessions so
Summit + Map look alive on first run. Reverse-engineer tip: wipe the app
data / reinstall to re-trigger seed, or delete rows from Logbook.

6. MAP SCREEN — flutter_map + OpenStreetMap
--------------------------------------------------------------------------------
File: lib/features/map/expedition_map_screen.dart

  TileLayer  → https://tile.openstreetmap.org/{z}/{x}/{y}.png
  userAgentPackageName → com.alexanderduckworth.wild_log  (OSM policy)
  MarkerLayer → one marker per session with lat/lng
  Icon        → ActivityType.icon + ActivityType.color
  ColorFilter → darkens tiles toward the rugged night aesthetic

Flow:
  sessionsProvider → filter hasMapPin → Marker onTap → SessionDetailScreen

No Google Maps billing. Free tiles. Portfolio story: "maps without a credit card."


--------------------------------------------------------------------------------
7. ADVENTURE DASHBOARD (SUMMIT)
--------------------------------------------------------------------------------
File: lib/features/dashboard/dashboard_screen.dart
Stats brain: lib/domain/dashboard_stats.dart

Shows:
  · Current day-streak (+ longest) — calendar days with ≥1 session
  · Totals: sessions, elevation m, distance km
  · fl_chart BarChart — sessions by activity type (icon labels)
  · Personal records — highest gain, longest distance, hardest difficulty
  · Next milestone — progressive session targets, then streak, then "keep fire"

Streak rule (read the code):
  Unique session dates sorted; consecutive calendar days.
  Current streak is 0 unless last activity day is today or yesterday.

Milestone voice:
  Motivating without gamification sleaze — purpose over profit.

Palette (Garmin × Arc'teryx field kit):
  voidBlack  #0A0E0C
  charcoal   #121816
  ridge      #1C2520
  lichen     #8FAE7E   ← primary action / life
  ember      #D4783A   ← difficulty / PRs / heat
  ice        #8FB4C4   ← snow / distance / cold
  bone       #E6EBE6   ← text
  mist       #9AA89E   ← secondary text
  trail      #3D4F44   ← borders

Typography:
  Display / callsigns → Barlow Condensed (letterspaced, outdoor gear catalog)
  Body / forms        → IBM Plex Sans (technical, readable)

Hard aesthetic rules used here:
  · Dark mode only (night after the trail)
  · Sharp corners (BorderRadius ~0–2) — gear, not candy
  · No purple gradients, no cream-serif brochure look
  · Activity "field callsigns" (TRAIL, WALL, LINE, RANGE…) over soft labels
  · Brand "WILD LOG" / screen "SUMMIT" as hero signals on the first tab

INFJ design decisions:
  Notes field copy invites meaning, not metrics theater.
  Milestone text frames consistency as integrity, not addiction.
  Seed notes sound like a real journal — reverse-engineer those strings
  if you want the app to keep feeling like yours.

10. HOW TO PRESENT THIS IN A PORTFOLIO
--------------------------------------------------------------------------------
Technical proof points (say these out loud):
  1. Riverpod reactive architecture with derived providers
  2. Drift/SQLite offline persistence with typed schema + seed
  3. flutter_map + OSM free tiles and typed markers
  4. fl_chart analytics from real domain aggregates
  5. Discriminated activity model (shared columns + JSON details)
  6. Custom design system proving UI taste beyond Material defaults

README job: hiring manager skim (tables, architecture diagram, run commands).
REVERSE_ENGINEERING.txt job: you, months later, remembering the WHY.
docs/talking_points.md job: 90-second interview voice.

  Summit (streak + chart) → Map (tap marker) → Detail → Edit note →
